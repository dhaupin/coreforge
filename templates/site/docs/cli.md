# The coreforge CLI

coreforge is a service, not a package you import into a build. It ships one
command, `coreforge`, with five site verbs and three release verbs. The site
verbs stamp a shell into your repo and keep its derived surfaces honest; the
release verbs are the ladder your `publish.yml` calls on a tag.

The identity lives once, in `site.config.js`. Every other surface derives from
it: the JS surfaces import the file, and the non-JS surfaces (`docs/_config.yml`,
`docs/freestruct.config.yml`, `web/ssr.config.js`, `robots.txt`,
`site.webmanifest`) are generated by `coreforge sync`. A brand census gate
refuses an identity literal that lives anywhere but the one file.

## The verbs

| verb | what it does |
| ---- | ------------ |
| `coreforge create [dir]` | scaffold the shell into `dir` from a `site.json` answer file or flags. Never clobbers an existing file. |
| `coreforge sync [dir]` | regenerate the derived surfaces from `site.config.js`. `--check` refuses drift instead of writing. |
| `coreforge build [dir]` | install the web deps if needed, then run the engine build (prestruct prerender plus the 404 repair). |
| `coreforge check [dir]` | run the gates over the tree. This is the verb CI calls. |
| `coreforge doctor [dir]` | the truth battery: config, placeholder residue, derived freshness, then the gates. Exit 0 is PASS only when nothing failed. |

The release verbs (called by the stamped `publish.yml`):

| verb | what it does |
| ---- | ------------ |
| `coreforge verify-release` | the post-publish trust ladder (`--npm`, or `--gh --tag vX.Y.Z --asset <name>`). |
| `coreforge release-notes <version>` | extract the CHANGELOG section for a version; empty output and exit 1 refuse a release with no notes. |
| `coreforge lint-packs [dir]` | run packstruct over the tree's own install. |

## Born: `create`

`create` reads the identity from a `site.json` in the target directory, or from
flags, and fills every token in the site template. It writes the site half
(`web/`, `docs/`, `site.config.js`, `.gitignore`, the `packs/` slot) and the two
CI lanes that belong to the adopter (a `test.yml` battery and a `publish.yml`
release ladder), both wired to the installed tool.

```bash
mkdir acme && cd acme
cat > site.json <<'JSON'
{
  "name": "acme",
  "url": "https://acme.creadev.org",
  "repo": "https://github.com/acme/acme",
  "docsHost": "https://docs.creadev.org",
  "docsBaseurl": "/acme"
}
JSON
npx coreforge create .
npm install
npx coreforge sync
npx coreforge doctor
```

A required answer that is missing is refused by name. A token that survives the
fill is refused too, because a half-filled site is worse than no site.

`create` never clobbers a file that already exists. Re-running it over a
stamped tree skips what is there and reports what it skipped, so you can pull a
newer template in without losing your edits.

## Kept current: `sync` and `sync --check`

`sync` regenerates the derived surfaces from `site.config.js`. Edit the config,
run `sync`, commit both. `sync --check` writes nothing and exits non-zero when a
derived surface disagrees with the config, which is what CI runs - so a hand
edit to a generated file fails the build instead of shipping.

## Proven: `check` and `doctor`

`check` runs the gates over your tree: docs frontmatter, links, style, fiction
signatures, the Liquid filter trap, theme parity, the language gate, the
birth-gate, and the brand census. It is the same gate set coreforge runs on
itself, reached through the installed package, so a gate fix arrives with
`npm update coreforge` rather than a re-copy.

`doctor` is the one command to run before you push. It fails on any of these:

- no `site.config.js` (the tree is not a stamped site);
- placeholder residue anywhere in the shipped tree - an unfilled template token,
  a leftover todo marker, a placeholder name left behind;
- a stale derived surface (`sync --check` disagrees);
- a failing gate.

Generated green is never shipped. An unfilled slot is a failure, not a warning.

## What the tool owns, and what you own

The tool half lives in `lib/` and travels by `npm install coreforge`. The site
half travels by `create` and is yours to edit. When a gate or a lane improves,
the tool half improves through the package version; your site keeps your brand
data. That split is why a stamped repo's `package.json` carries one
devDependency (`coreforge`) and nothing else at the root.
